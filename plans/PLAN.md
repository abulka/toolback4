# toolback v4 — Plan & Progress

A modern ToolBook spiritual successor: book → pages → objects, authored visually,
scripted in plain JavaScript. Fourth attempt — informed by the post-mortem of
`../pyinvent`, `../toolback`, `../toolback-lite`, `../toolback-lite-vue3`
(those folders are archived reference material; salvage ideas, not code).

**Status: M0–M5 + M6a + M6b + M6c complete — v1 loop finished; backlog shipping**
(see [Milestones](#milestones) and [Progress log](#progress-log)).

---

## Goal & locked decisions

Personal joy project (nostalgia + fun). Not a product; multiplayer/SCORM/analytics are
non-goals for now.

| Decision | Choice | Why |
|---|---|---|
| Framework | Vue 3 + Vite + TS | Continuity with prior attempts; known well |
| Layout model | Absolute position + fluid pages + edge constraints (CSS `left`/`right`/`top`/`bottom` distances) | Least painful approach across all attempts (pyinvent proved it); grid libraries stalled two attempts. Breakpoints/`Book.canvas`/`Book.design`/glue are gone — each control stores the page/group edges it follows (Page simplification, 2026-09-16) |
| Persistence | Local-first: `.toolbook.json` file + IndexedDB autosave | No backend for v1; Redis/S3/Firebase killed attempt #2 |
| Canvas | Sandboxed same-origin iframe | Editor survives broken user scripts; design/run isolation (toolback's F3 pattern) |
| Drag layer | Custom, pointer-events, zero drag-drop deps | Both prior stalls were grid-library internals (`calcXY`, `@noction` fork) |

### Page simplification — options considered and rejected

Shipped 2026-09-16 (see the progress log). The durable reasoning, kept here so a
future reader can judge the model on its merits:

- **Make the existing breakpoints editable** (the original request: resize,
  rename, add, delete and reorder them). Rejected — it would enshrine and
  multiply the "sizes × backgrounds" problem instead of removing it.
- **Keep the proportional glue engine indefinitely.** Rejected — it needs a
  stored "designed at" reference size and proportional-scaling semantics that
  are surprising and hard to explain; fixed edge distances express the same
  layouts plainly.
- **Drop preview widths and test by resizing the editor window.** Considered;
  kept the presets (Phone 390, Tablet 768, …) because shrinking the editor to a
  phone width is impractical and the presets are an editor setting only (they
  never touch the book).
- **Fit as a named state/toggle in the breakpoint list.** Dropped once preview
  widths were reframed as artificial viewport restrictors (Chrome device-toolbar
  style) rather than page sizes.
- **Proportional "scales with the page" positioning** (the old
  `left`/`top`/`right`/`bottom`/`stretch`) — deliberately dropped in favour of
  fixed distances plus **follows both (stretches)** and **centred**. Old
  proportional controls migrate to their nearest fixed-distance equivalent, so a
  legacy layout can shift slightly at non-reference sizes; accepted, with the
  example books as the regression net.
- **A separate "pinned to the window / sticky" option** — considered and left
  out. Follows bottom/right mean distance to the page box edge; always-visible
  window glue would be a separate future choice, not overloaded onto them.

## Architecture

pnpm monorepo. Dependency direction: `format ← controls ← runtime ← editor`.

```
toolback4/
├── packages/
│   ├── format/      # Book/Page/Object zod schemas + factories. Zero runtime deps beyond zod.
│   ├── controls/    # Control renderers (plain DOM + CSS design tokens): button, label, input, image, card, container
│   └── runtime/     # Player. Plain DOM, NO Vue. Renders JSON, runs scripts, editor message protocol.
└── apps/
    └── editor/      # Vue 3 + Pinia + Monaco(M2). Palette | iframe canvas | properties.
```

### Data model (packages/format)

```ts
Book        { id, title, backgrounds: Background[], pages: Page[] }
Background  { id, name, color, objects: PageObject[] }
Page        { id, name, script, backgroundId, size?{w,h}, objects: PageObject[] }
PageObject {
  id, name,                       // name = unique per page+background, the `controls[name]` handle
  control: 'button'|'label'|'input'|'image'|'card'|'container'|'switch'|'group'|'markdown'|'html',
  x: XEdge, y: YEdge,             // the page/group edge distances this object follows
  props: Record<string, unknown>, // control-specific (e.g. { text })
  on: Record<string, string>,     // eventName -> script
}
XEdge = { mode:'left'; left; width } | { mode:'right'; right; width }
      | { mode:'both'; left; right } | { mode:'center'; width }
// YEdge mirrors with top/bottom/both/center
```

Backgrounds are the ToolBook shared-page resource: their objects render under
every member page (fully live at run time). A page with no `size` is fluid —
it fills the window and grows with content placed from the top/left only — while
a `size` makes it a fixed surface (dialog / popup / plugin window). Controls are
rendered straight to CSS from their edge distances, so the browser repositions
them on resize with no re-render. Legacy books migrate on `parseBook` (one
background per distinct page colour; then `canvas` desktop size → the reference
the old `rect`+`fit` pairs are frozen against into `x`/`y`, and a background
`size` → its pages' `size`).

Schema is stable from day one; renderers for the controls fill in across milestones.

## Documentation conventions

- **`docs/scripting-guide.md` is the canonical scripting reference** — the in-app `?` buttons
  (next to "Page script" and "Script") open it rendered as HTML, jumping to the relevant
  section. It is imported into the editor via Vite `?raw`, so the file in `docs/` is the
  single source to edit.
- **Keep it current**: any change to the scripting API (`store`, `controls`, `page`, events,
  dynamic labels) must update the guide in the same milestone.

### Runtime & scripting

- Scripts run via `new Function` inside the canvas iframe with an injected API:
  `page`, `controls.<name>`, `store.get/set` (reactive; powers `{{key}}` dynamic labels),
  plus real `fetch`/async-await for free.
- Event wiring: explicit `on: {}` per object **plus** the validated "top-level
  `function click()` = event" sugar (regex-scan; see salvage list).
- Design-time input suppression: `pointer-events: none` on canvas content; editor
  overlay captures pointer events (replaces toolback's `eventPause.js` hack).

### Persistence & export

- Open/save single `.toolbook.json` via File System Access API; IndexedDB autosave.
- Publish (M4) = one-click standalone HTML (runtime + embedded JSON), all in-browser.

## Copy / paste — design & future-proofing notes

Shipped 2026-09-13 (⌘C/⌘X/⌘V; see Progress log). One in-app clipboard mirror in the
store (`stores/book.ts`) holds a deep JSON clone of the top-level selection; copy/cut
also write a `{ "__toolback": 1, "objects": … }` tagged payload to the system clipboard
(`copyJson.ts`). Paste re-ids/re-names, offsets +24px, cascades on repeat, targets the
selection's group (else top level). Copy = no undo step; cut/paste = one each.

**Why copy/paste is future-proof by construction:** both copy and paste deep-clone the
*whole* object graph as opaque JSON (`JSON.parse(JSON.stringify(…))`), not field by
field — so any future leaf on `PageObject` (style, states, accessibility, renderer
data, …) automatically rides through copy, across containers, and back through paste.
Only proviso: values must be JSON-serializable, which is already a book-wide structural
constraint (the book always crosses the iframe as a JSON clone).

**Known limitations** (as of the shipped build):

1. **Re-id/re-name recurses only into `children`** — `cloneObjectTree` regenerates
   `id`/`name` for the object and its group members. If the format later gains a
   *second* nested container with its own ids/names (e.g. `states: […]`, `layers: […]`),
   those nested ids would be copied verbatim → duplicate handles/collisions. New leaf
   fields are safe; nested-identity fields are not.
2. **No per-instance freshness for arbitrary new fields** — anything a future feature
   needs regenerated per copy (a UUID, a unique key outside `id`/`name`) is copied
   as-is. Same limitation duplicate already has.
3. **Envelope is version-locked (`__toolback: 1`)** — `parseClipboardJson` rejects any
   other version (safe: never misparses). The app-side paste only reads the in-app
   mirror, so the envelope version doesn't gate the core flow; it matters only if an
   OS-clipboard paste path is wired up later.
4. **Paste doesn't re-validate via zod** — pasted objects bypass `PageObjectSchema.parse`,
   so no default backfill on paste. Harmless today (the mirror came from a validated
   book); only relevant if paste ever reads the OS clipboard.

**Potential hardenings** (deferred — do when a future feature needs them, not before):

- **`refreshObjectIdentity(src, freshName)` seam** — extract a single identity-refresh
  seam from `cloneObjectTree` (recursing `children` today) so a future nested container
  is one registration point instead of a rewrite of the clone logic.
- **Schema-parse on paste** — run pasted clones through `PageObjectSchema.parse` to
  backfill new defaults and catch schema drift (~3 lines, belts-and-braces).
- **Version-tolerant envelope** — accept `__toolback >= 1` to smooth cross-version
  copy/paste if the payload shape ever evolves.

Fix (`packages/runtime/src/design.ts`): new pure `scrollClampShift({viewport, scroll, padding, rightFixed, rightMoved, bottomFixed, bottomMoved})` iterates the page size vs the scroll clamp to find the nudge that keeps the dropped object's on-screen position; `compensateMoveForScroll` runs it at pointer-up and shifts the committed rects. No-op when not scrolled or when other content still overflows; top-level moves only (a moved group member re-hugs its group, not predictable in the canvas). Docs: internals §4 Drag bullet. Tests: +3 `scrollClampShift` cases. **typecheck clean, 446/446 vitest**, verified in-browser (dropped at screen x=334 stays at 334 instead of snapping to 604; page-absolute x compensated 604→334).

- **2026-09-17** — **Fix: Sel-mode page-padding shading showed even when the padding was masked.** Report: selecting a left/top button well inside the window (content+padding < window) still showed the padding bands in **Sel** mode. The gate only checked that the selection followed the near edge, not that the padding was doing anything. Fix (`packages/runtime/src/design.ts`): in `selected` mode a band now also requires the padding to be "in effect" on that axis — `bounds.w > document.documentElement.clientWidth` (right), `bounds.h > clientHeight` (bottom), i.e. the page is content-sized. So a window-sized page shows nothing; once the page overflows, the near-edge selection shows the real gap. **All** mode is unchanged (still outlines the configured padding even when masked). Docs: guide springs + internals edge-springs. Tests: split the Sel padding test into an in-effect case (small viewport → bands) and a masked case (large viewport → none, All → 2). **typecheck clean, 447/447 vitest**, verified in-browser (Window 1006px: page fits → Sel 0 bands; Phone 390: page 710 wide → Sel 1 right band since only width overflows; All → 2).

- **2026-09-17** — **Text-style round-out: bold/italic/align + split text-colour/background, grouped across a selection (shipped).** Controlled, deliberately small formatting set (no borders/radii/shadows/gradients/opacity — the CSS-engine tail stays out). **Data (`@toolback/format`):** optional props `bold`, `italic`, `textAlign` (`left|center|right`), `vAlign` (`top|middle|bottom`), `textColor`, `background`; `TEXT_ALIGNS`/`VERTICAL_ALIGNS` + `resolveTextAlign`/`resolveVerticalAlign`, and `TEXT_STYLE_KINDS`. `color` keeps its role meaning (surface fill for buttons/cards/containers, text for labels/viewers, track for switches); `textColor`/`background` are explicit per-role overrides that win over `color` — so a label can carry both a text colour and a fill. **Renderers (`@toolback/controls`):** one `applyTextStyleToTree(el, obj)` replaces the old `applyStyleProps`, resolving which node each kind paints (switch text span, card title+body, viewers root, etc.); fixes the previously ignored `color`/`textColor` on inputs; HTML viewers gain styling.
